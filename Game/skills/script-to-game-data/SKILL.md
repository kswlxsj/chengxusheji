# 剧本 → 游戏 JSON 转换 skill

本 skill 服务于本仓库的“事件驱动剧情框架”（见 `Game/README.md`）：把编剧写的剧本（Markdown 文本）转成框架数据 JSON 的**候选产物**与**审查清单**，供人工审阅后再落地。它不是通用编剧，不做数值设计，不删改原文。

- 规范细节：见同目录 [`转换规范.md`](转换规范.md)（必读）。
- 策略常量：见同目录 [`config/policy.json`](config/policy.json)（可调）。
- 工作示例：见同目录 [`samples/样例说明.md`](samples/样例说明.md) 及配套样例文件。
- 空白清单模板：见同目录 [`templates/剧本转换审查清单-模板.md`](templates/剧本转换审查清单-模板.md)。

## 何时使用

- 用户要求“把剧本转成游戏数据 / JSON”、“按剧本生成事件”、“转换/清洗剧本”等，并给出输入文件。

## 何时不使用

- 用户只是讨论剧本内容、数值设计、框架功能——不执行转换。
- 未明确指定输入文件，或指定文件不存在、不可读、不是剧本正文（如会议记录、规则书、图片清单）。

## 输入要求（第一步，不可跳过）

1. 向用户确认输入文件：**一个或多个** Markdown 剧本文件的路径。路径可为仓库内（如 `Assets/Text/剧本.md`）或仓库外绝对路径。
2. **用户未指定时：暂停并询问**。允许给出候选文件清单与“放弃”选项；不得自行默认仓库内某个文件、不得沿用上次输入。
3. 校验：文件存在、可读、UTF-8 文本；内容确实为剧本正文（含“事件”编号类结构）。
4. 多个文件时确认其关系（顺序连载 / 不同版本 / 各自独立），关系不明或事件编号冲突时**暂停询问**。
5. 转换过程中不得修改输入文件。

## 硬红线（违规即失败）

- 只允许输出到白名单 JSON（见 `policy.json`）；`attributes.json`、`skills.json`、`schemas/`、`src/`、`tools/`、`compiled-game-data.js`、`assets/` 永不写入。
- **只增不删改**：不删改、不重写剧本原文词句；只做格式清洗。JSON 候选是“部分派生物”——无法无歧义落地的内容一律**不进入** JSON，只进审查清单，绝不编造替代文本或数值。
- **不设计数值与规则**：不发明修正值、骰面、属性/技能、怪物数值、坐标；检定对象只允许直接命中的已注册属性；骰子参数只从原文直译。
- 凡自动推断（拆分、合流、旗标、跳转接线）必须逐条以类别 A 记入审查清单。
- 悬空跳转目标、ID 冲突、无法辨识的结构 → **停止并询问**，不猜测。

## 工作流

1. **确认输入**（见上）。
2. 读 `config/policy.json` 与 `转换规范.md`；读 `data/attributes.json`、`data/skills.json`、`data/items.json`、`data/scenes.json`、`data/events.json` 建立注册表快照（只读）。
3. 逐事件解析剧本（见 `转换规范.md` 语法映射表），生成候选 JSON 片段：
   - 事件 ID 用 `policy.json` 的模板（默认 `E_0NN`，连字符转下划线、保留零填充）；
   - 与既有数据 ID 冲突时停止询问；
   - 未落地项以原文整行 `dialogue` 占位（见策略），分支原文不入 JSON。
4. 按 `templates/剧本转换审查清单-模板.md` 复制并替换占位符，生成审查清单到 `Game/docs/剧本转换审查/剧本转换审查清单-YYYY-MM-DD-HHmm.md`（目录与分钟级时间戳规则见 `policy.json`；每次转换新建文件，不覆盖旧文件）。清单保持**精简、可直接编辑**：头部字段 + “待你决策”编号条目（位置/类别/建议/决策/备注）+ 补充说明 + 收尾；格式、类别标记与决策词表见 `转换规范.md` §13。
5. **隔离验证**：把 `Game/` 整体复制到系统临时目录，注入本次候选（必要时注入隔离占位事件与示例场景），在临时目录运行 `node tools/compile-data.mjs`，断言编译成功且无悬空引用，随后删除临时目录。真实 `data/` 不得被编译写入。
6. **停在第 1 闸门**：告知用户清单路径与待决项概览，请用户**直接在清单文件上填写“决策”**（可在“备注/补充说明”追加说明），完成后回复“已修改，继续”；agent **重读用户修改后的清单**再继续。闸门未开前不得写 `data/`、不得提交。

## 执行节奏：三段强制确认闸门（不可跳过、不可合并）

任何一次转换都从 **candidate（第 1 闸门之前）** 开始，即使使用者已口头给出部分决策；每一道闸门都必须得到使用者的**明确批准**后才能通过。批准可以在同一会话内随后给出，但 agent 不得擅自跳闸、不得把“清单审阅”与“写入数据”合并成一步。**审查清单是人与 agent 之间唯一的决策台账**：使用者直接在清单文件上填写决策（决策词表见 `转换规范.md` §13.3），agent 只认用户改后的文件、以“决策”行首词执行。

1. **第 1 闸门 · 决策闸（candidate 结束点）**：清单与候选就绪、隔离验证通过后，**停止**并告知清单路径；等使用者在文件上逐条填“决策”（类别 A 条目可推翻、其余给批准/修改/否决/转交/留待）并回复“已修改，继续”。agent **重读修改后的清单**再继续。未获批准：不写 `data/`，不进入 landing。
2. **第 2 闸门 · 改动方案确认闸（landing 写入前）**：使用者已在清单完成决策并回复“按清单落地”后，agent 先把**逐文件改动方案（diff 草稿）**摆出来；使用者逐文件确认（尤其 `scenes/items/meta` 涉及设计输入）。确认后才把候选写入白名单 JSON。
3. **第 3 闸门 · 终审闸（提交前）**：写入后在真实仓库执行 `node tools/compile-data.mjs`（报错即回滚修复，不蒙混），随后汇报 diff 与编译结果；使用者终审通过后，才按仓库规范做中文原子 git 提交。

说明：第 2、3 闸门之间的“写入→验证→终审”属于同一次落地运行的连续动作，但仍以终审为提交前置条件；任何一步使用者要求“先等等”，agent 就地停止等待。

## 验收

- 候选 JSON：全部 ID 合法且唯一、无悬空引用、只引用已注册属性/场景；`node -e "JSON.parse(require('fs').readFileSync('文件','utf8'))"` 可解析。
- 审查清单覆盖每个事件中的：非直译检定、SAN、前提/条件、物品获得、表现指令、文本疑点。
- 无任何用户未同意的推断悄悄落地；输入文件未被改动；真实数据文件未被改动。
