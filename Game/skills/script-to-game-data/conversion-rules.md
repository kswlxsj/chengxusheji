# 剧本转换规范（webGame 框架）

> 本规范是 `SKILL.md` 的完整规则手册。执行转换前先读本文（规则细节以 SKILL.md 与本文为准，无独立配置文件）。全文示例取自仓库内现行剧本（`Assets/Text/剧本.md`，事件编号 E-001~E-031）。

## 1. 目的与总原则

把“剧本”形式 Markdown 清洗为框架 JSON 候选。剧本是 TRPG 主持人文本，不是点选游戏脚本；框架是“场景物件 + 顺序事件 + 分支”的解释器（数据接口见 `Game/README.md`）。两者之间由本规范做**保守、可复核**的翻译。

四条总原则：

1. **只增不删改（针对剧本原文）**：任何词句、标点、破折号原样保留；只做格式清洗。剧本文件永不被修改。
2. **不设计数值与规则**：转换器不发明修正值、骰子、属性技能注册、怪物数值、坐标、物品注册。文本中自带的数值只做“直译”（如骰子参数）。
3. **候选 JSON 只含可无歧义落地内容**：无法落地的内容（技能检定、%修正、对抗、跨路径条件、物品、舞台指令等）一律**不入 JSON**，转写进审查清单并保留原文引用；必要时在事件流中放入**原文占位行**（见 §9），绝不编造新文本。
4. **自动推断必须登记并经确认**：任何结构性推断（事件拆分、分支命名、旗标、合流）以类别 A 记入执行台账（见 §13），并在正文为需要你拍板者生成一条人话提问；未经答复确认不得静默落地。

## 2. 输入准备

- 输入文件由用户指定（一个或多个），未指定则暂停询问（见 SKILL.md）。
- 只读快照：`data/attributes.json`、`data/skills.json`、`data/items.json`、`data/scenes.json`、`data/events.json`。其中 `attributes.json` 的 `name ↔ id` 对照与 `skills.json` 的 `name ↔ id` 对照是本规范运行时唯一允许的动态查表。
- 检查工作区：用户未提交的更改保留不动；确认远端无新提交后再动手。

## 3. 文本预处理（仅格式清洗）

| 处理 | 规则 |
| --- | --- |
| Markdown 标记 | 删除 `**`、`*`、`#` 标题符、`-`/`*` 列表符、行首缩进与全角/半角空白差异；**文字本身一字不改** |
| 全角空格/制表 | 仅删除“排版性”空白（行首缩进、空行），句内空白保留 |
| 编码 | 输出统一 UTF-8，全角标点保留原文 |
| 事件标题 | 只提取“事件 ID 与主题”；标题文字登记进清单（类别 O：标题登记；JSON 无注释位） |
| `//` 注释块（KP 备注） | 不执行、不转录进 JSON；原文进审查清单（如 E-023 的机制说明） |

## 4. 结构解析模型

### 4.1 事件块

- “事件”标题：正则 `事件\s*([A-Za-z0-9_-]+)`（如 `E-001`）。匹配即开启新逻辑事件块，到下一个同级或更浅标题结束。
- 编号无法辨识 → 停止并询问（阻断情形）。
- 每个逻辑事件块转换为若干**运行时事件**：运行时事件是原子单元（动作顺序执行；`check`/`choice` 是事件边界，目标必须是别的运行时事件；无 `next` 的运行时事件执行完即回到场景）。

### 4.2 链、分叉与合流

- 块内若只有一个线性序列 → 单个运行时事件；块尾“（无分支，均进入 E-0xx）”或“（→E-0xx）”写成 `next`。
- 块内含 `check`/`choice`/SAN 检定（它们都是边界）→ 拆成“入口事件 + 分支片段事件 + 公共后续（合流事件）”。合流时各分支事件 `next` 指向同一个合流事件（命名见 §10），不复制公共文本。
- 块级文本出现在所有分支之后（如 E-008 尾部“在不安的驱使下，你来到五号车厢。”）→ 属于公共后续，放进合流事件；两条分支都汇入。
- 只在一个分支内的文本 → 只放该分支片段事件。
- 分支后无公共文本、检定的某一侧又“无事发生”时，见 §6.2 的端点约定。

### 4.3 需要人工的触发拓扑

以下不在转换器能力内，只进清单（类别 H），并给出建议：
- “可调查：X → E-0NN”的热点物件（坐标/贴图/场景归属）；
- 何时开放调查、可否重复调查（如 E-004 地图是否只可看一次）、检定的触发时机（如 E-001 的灵感检定由谁触发）；
- 车厢推进逻辑（哪个门/对象把玩家带到下一场景；中途“放弃”路线如何汇合）。

## 5. 语法映射总表

| 剧本写法 | 输出 | 备注 |
| --- | --- | --- |
| 叙述段落 | `{ "type": "dialogue", "text": <原文> }` | 每段一个动作；段落间空行不输出 |
| `（说话人）正文`（括号内无冒号） | `dialogue` + `"speaker": <说话人>` | 正文为去前缀原文 |
| `（主角表情：惊恐）正文`、`（场景：抖动）` 等舞台指令 | 纯指令行不入 JSON；“指令+正文”整行原样 `dialogue` 转录 | 指令本身登记类别 F |
| `（可调查：A → E-0xx；B → E-0yy）` | 不入 JSON；目标事件照常单独生成 | 登记类别 E/H |
| `（选择：A→E-0xx；B→E-0yy）` | `choice`；每项 `label` 用选项原文，`next` 用目标运行时事件 ID；`prompt` 无原文时置空串并在清单登记 | 选项过滤后无可用项会运行时报错：无条件项全保留 |
| `（检定：<属性名>）` | `check`（见 §6） | 仅限属性 |
| `（检定：<技能名/其他>）` | 不入 JSON；原文行 `dialogue` 占位 | 分支原文登记类别 C |
| `（分支N：成功/失败）…` | 各分支块 → 独立片段事件 | 缩进与编号仅用于分块识别 |
| `（若<前置结果>：<内容>）` | 见 §8 | 只处理可直接追溯的 |
| `（前提：<前置结果>）` | 事件文本照转；显隐条件建议登记类别 E/H | 落地时物件的 `visibleWhen` |
| `（→E-0xx）` / `（无分支，均进入E-0xx）` | `next: E_0xx`（映射后 ID） | 悬空 → 阻断 |
| `（SAN …）` | 见 §7 | |
| `（获得钥匙/手机…）` | 不入 JSON；物品注册建议登记类别 D | 未注册物品会编译失败 |
| 标题内注记如 `（医学）` | 不入 JSON | 进清单“标题登记” |
| 拉杆列表等 `-` 行 | 去掉列表符后逐行 `dialogue` | 保留原文内容 |

## 6. 检定处理决策树

### 6.1 直译条件（全部满足才直译）

1. 检定词**精确等于**某已注册属性的 `name`（运行时从 `attributes.json` 现读对照，如 灵感→insight、力量→strength、体质→constitution、敏捷→agility、幸运→luck）；
2. 无“修正”（手电+10% 之类为百分制修正，框架是 1d6+属性 判定，语义不可迁移）；
3. 无“或 / 二选一 / 对抗 / ×N / 自动成功”等附加语。

输出：

```json
{ "type": "check", "checkId": "ev001_insight_01", "attribute": "insight", "success": "E_001_S", "fail": "E_001_F" }
```

不改写 `modifier`（缺省为 0）。分支文本按 4.2 进各自片段事件。

### 6.2 端点约定（“无事发生”分支）

- 分支后无文本且其后无公共内容 → 分支片段事件 `actions: []`（编译器与运行时均接受空动作事件，见 `tools/compile-data.mjs` 与 `src/events.js`），命名 `E_0NN_<后缀>_END`。
- 分支有内容 → 内容放该片段事件；尾部若接公共内容用 `next` 合流。

### 6.3 不可直译（一律占位 + 清单）

命中技能名（侦查/医学/急救/话术/潜行/投掷/图书馆/魅惑等）、技能未注册（图书馆/魅惑）、带修正、`或`组合、对抗、`×2`、自动成功、多检定组合（如“话术&侦查”）等 → 不生成 `check`；在事件流当前位置放入原文整行占位 `dialogue`；分支文本不转录，原文整块登记进清单（类别 C，含推荐出路：注册技能、人工映射到属性+人工修正、或等框架支持技能检定）。

### 6.4 运行时事实（写报告用，不是可依赖能力）

当前 `src/events.js` 的 `check` 实现为 `1d6 + 属性值 + modifier >= 11`（README 的 d100 描述已过时）；且存在一个硬编码特例 checkId（`carriage02_stealth_half_luck_001`，幸运半值）。这些属于框架层事实：转换器不得生成依赖硬编码特例的内容，也**不改动 src**；若剧本需要这类规则 → 登记类别 F（框架缺口）。

## 7. SAN 语义与骰子

剧本 SAN 记法（CoC 惯例）：`SAN X/Y` 或 `SAN 减少 X/Y`，其中 X/Y 各为整数或骰子表达式 `NdM`（含 `1d2`）。语义 = SAN 检定：成功损失 X、失败损失 Y。

| 情况 | 输出 |
| --- | --- |
| 无条件 SAN 行 | 拆出 SAN 检定：`check`（attribute 为该 `san` 注册 id、checkId 按 §10），成功/失败目标按损失额落事件 |
| 损失 0 | 该侧直接指向后续合流/端点（§6.2），不写动作 |
| 损失为整数 | `modifyAttribute`，amount 为该整数的相反数 |
| 损失为骰子 | `custom`：`{"name": "modifyAttributeByDice", "params": {"attribute": "san", "direction": "loss", "count": <N>, "sides": <M>, "bonus": 0, "label": "SAN"}}`（动作已由 `src/custom-actions.js` 注册；参数从原文直译） |
| `SAN 归零` | `modifyAttribute` amount 取该属性注册 `max` 的相反数（运行时把属性钳制到 `min` 即 0，从而触发终止逻辑进结束页） |

示例（剧本 E-006）：
- `（若E-005灵感成功：SAN 0/1）` → 归入“成功侧”变体事件：SAN 检定成功侧无动作直达端点；失败侧 `modifyAttribute san -1`。
- `（若E-005灵感失败：SAN 1/1d4）` → 归入“失败侧”变体事件：成功侧 `-1`；失败侧 `modifyAttributeByDice 1d4`。

登记：每次 SAN 行转换都在执行台账登记「约定 C1」（自动推断，类别 A）。正文向审阅者呈现一条人话提问（如：*剧本中 `SAN X/Y` 我一律按“SAN 检定：成功扣 X、失败扣 Y”处理，符合原意吗？*）。约定 C1 属约定级条目（§13.6）：同一约定在历史审查清单中已被批准且未见变更时，本批只合并出一条「沿用上次已批准的约定？」确认，不重复逐条提问。

## 8. 条件（若/前提）与旗标

- 只处理**可直接静态追溯**的（若/前提）：
  - 前置检定就在本事件块的直接入口（如 E-005 判定后进入 E-006 时按成败走不同变体）→ 把下游事件按前置结果拆成变体片段（如 `E_006A`=E-005成功侧、`E_006B`=失败侧），拆法与依据登记为自动推断（类别 A）；
  - 前置结果是之前某检定的成败且当前结构恰好在其分支路径上 → 在该分支片段首动作加 `setFlag`（键名 §10），供未来落地使用。
- 跨路径条件（玩家可从多条路线到达同一事件，如 E-021“若此前未去过7号车厢”、E-018“前提：E-016背起乘务员”）：框架没有“按旗标选择动作”的原子能力（条件只出现在 `choice.options[].when` 与物件 `visibleWhen`），转换器**不拆**；事件按线性公共部分转录，条件原文与推荐落地方案（物件显隐/选项条件/合流拆分）登记类别 C/H。
- 事件本身带“前提”（如 E-011 前提 E-008侦查成功）→ 建议落点为“场景物件 `visibleWhen: {"flag": "ev008_scouting_ok", "equals": true}`”登记类别 E/H。

## 9. 占位规则

- 无法落地的检定/条件指令：在事件流当前位置放一个 `dialogue`，text = **该行原文**（如“（检定：医学）”），后续公共文本照常继续；分支/条件原文整段只进清单。
- 占位不属于“发明文本”：它是原文转录。人工落地后删除占位行。
- 纯舞台指令（无正文）不转录（见 §5 表），只进清单。

## 10. 命名与 ID 约定

框架要求 ID 匹配 `^[A-Za-z][A-Za-z0-9_-]*$`（见 Schema），故所有中文只能出现在 `name/text/speaker/description` 等展示字段。

| 用途 | 规则 | 例 |
| --- | --- | --- |
| 事件（来源编号） | `E_` + 编号原样（连字符转下划线，保留零填充） | `E-001` → `E_001` |
| 派生片段 | `E_0NN` + `_S`/`_F`（检定成败）、`_A`/`_B`（前置变体）、`_JOIN`（合流）、`_END`（空端点） | `E_006A`、`E_008_S` |
| 检定点 checkId | `ev` + 编号去零 + `_` + 语义词（如检定词） + `_01` | `ev001_insight_01`（全局唯一，编译器会查重） |
| 旗标 | `ev` + 编号去零 + `_` + 语义词 + `_ok` / `_fail` | `ev005_insight_ok` |
| 后续同名源事件 | 同一 剧本 编号多次出现（如来源不同版本同号） | 冲突时停止询问 |

派生后缀在**同一来源事件内部**需唯一；不同来源事件可用相同后缀。命名冲突（含与既有 `data/events.json` 中任何事件 ID 冲突）→ 停止询问。

## 11. 输出白名单与写入规则

| 文件 | 状态 |
| --- | --- |
| `Game/data/events.json` | 落地模式可写：仅**追加**新命名空间事件，不改动既有条目 |
| `Game/data/scenes.json`、`Game/data/items.json`、`Game/data/meta.json` | 落地模式可写，但**每处都须由用户确认**（素材/坐标/物品注册属于设计输入，不在转换器默认职权） |
| `Game/data/attributes.json`、`data/skills.json` | 永不写（只读对照） |
| `schemas/`、`src/`、`tools/`、`styles/`、`data/compiled-game-data.js` | 永不写；编译由人工执行 `npm run compile` |
| `assets/` | **默认不写**；允许两类**新增**：①审阅者勾选「委托占位补位」时生成的简单占位 SVG（§13.5）；②素材盘点时从源目录 `Assets/` 按命名检索命中后**复制**的图片副本（自行改名，§13.5）；**既有 `assets/` 文件与源目录 `Assets/` 永不改动** |

- 同一来源事件已存在（重跑/增量）→ 更新其自身条目属允许的“追加式修订”，但落地前必须 diff 给用户。
- 所有写操作保持 JSON 缩进风格与既有文件一致（2 空格，见现有文件）。

## 12. 素材映射建议表（产出汇入清单「素材指定区」，见 §13.5）

- 每处“可调查/场景切换”给出建议行：`建议物件 id / 名称 / 可能贴图来源（Assets/Image/… 或 assets/… 现有文件名）/ 所属场景 id 建议`；并标注素材依赖三态：**已存在**（给出路径）/ **缺失** / **推断占位**（注明转换时的假设，如“暂沿用现有背景”）。
- 建议行统一汇入审查清单「素材指定区」，由审阅者显式指定（沿用 / 新建 / 委托占位补位 / 暂缓，见 §13.5）；**agent 不得自行选定既有 `assets/` 文件**（「委托占位补位」生成占位与「从 `Assets/` 检索复制」属授权例外，见 §13.5）。
- 坐标、zIndex 等布局数值**不猜**，留空待人工。
- 场景 id 建议沿用 `carriage_06` 风格（如 `carriage_07` 已存在）；背景图对照参考 `Assets/Image/Scene/Background/` 与 `assets/` 现有文件。

## 13. 审查清单：格式与读取规则

清单是人与 agent 之间唯一的决策台账，落盘 `Game/docs/conversion-reviews/review-checklist-YYYY-MM-DD-HHmm.md`（固定目录、分钟级时间戳、每次转换**新建文件**不覆盖旧文件）。空白模板（含全部占位符与说明）见 `templates/review-checklist-template.md`，agent 生成清单时复制模板并替换 `{{…}}`。

**面向审阅者的设计原则：正文只呈现「人话提问 + 素材指定」，agent 内部逻辑一律封装，不作为审阅者默认知识。** 本规范各处“登记进清单（类别 X）”统一起义为：记入文末「执行台账」（带类别字母，§13.2）；是否生成正文条目由 agent 按 §13.4 判断。

### 13.1 结构（审阅者视角，从简、可直接编辑）

1. **先读这里 / 头部**：上手说明 + 少量固定字段（剧本、输入文件、生成时间、skill 版本、产出状态、事件范围、隔离编译验证结果、候选概况）。
2. **一、请你判断的 N 件事**：每条含剧本原文短引、「我的处理」（一句人话，不出现内部行话）、「请你判断」（实际问题）、建议、按建议 / 若跳过的后果、勾选作答行（同意 / 需要调整 / 本次跳过）+ 说明。**一条只承载一个决策点。**
3. **二、素材指定区**：逐行列出候选 JSON 的素材依赖（§13.5），每行须有审阅者显式结果。
4. **补充说明**：审阅者自由书写区（用 `#Q1` / `#M1` 引用条目）。
5. **收尾**：固定口令提示（§13.7 与模板收尾）。
6. **附录 · 执行台账**（agent 内部用，审阅者可忽略）：按编号映射 {剧本位置 / 类别 / 内部引用 / 落地动作 / 落点文件 / 用户答复 / 状态}。

### 13.2 类别标记（仅作执行台账内部字段，不作为审阅者阅读前提）

`A` 自动推断 ｜ `C` 检定规则 ｜ `D` 数值物品 ｜ `E` 素材场景 ｜ `F` 框架缺口 ｜ `G` 文本问题 ｜ `H` 触发拓扑 ｜ `O` 其他

### 13.3 作答词表（审阅者在每条「我的答复」勾选；agent 只认这些词）

| 作答 | agent 内部语义 |
| --- | --- |
| 同意 | 按该条「建议」落地（≈原“批准”） |
| 需要调整 | 按该条「说明」中的替代方案执行；说明没写替代 → 停下问该条（≈原“修改”） |
| 本次跳过 | 该项不落地（候选保留为“仅候选”）；去向以「说明」为准记台账，如“交框架组 / 随下批”（≈原“否决 / 留待 / 转交”按说明细分） |

无法辨识的作答（勾选缺失、说明与勾选冲突）→ 停下逐条追问，不猜测。

### 13.4 正文条目生成规则（agent 登记 → 呈现）

- 每条登记先判断呈现形态：
  - **需要你拍板**（是否认可推断 / 如何落地 / 是否改动文本等）→ 正文生成一条人话提问（Q）：标题即要拍板的事，正文含剧本原文短引与「我的处理」；**禁止**把类别字母、候选事件 ID、命名/接线、checkId 等内部细节当作可读前提（它们放执行台账）；
  - **素材依赖**（§12 / §13.5）→ 正文素材指定区一行（M）；
  - **纯信息**（如标题登记、已批准约定的沿用提示）→ 只写进「补充说明 / 汇总」，不占提问。
- 一条提问只承载一个决策点：旧式复合条目（如“拆分 + 两处接线”）必须拆成逐条提问。
- 每条提问附「若按建议 / 若本次跳过」的影响说明，让审阅者知情决策。

### 13.5 素材指定区（新增；每行必须有显式结果，闸门 1 才通过）

- 行内容（agent 填写）：
  1. **依赖**：哪个场景 / 哪些候选事件需要该素材（人话 + 内部引用如 `changeScene → carriage_07`，供 agent 定位）；
  2. **所需形态**：素材类型（场景背景图 `scene.background` / 物件贴图 `object.image` / 物品图标 `item.image`，均 assets/ 下文件）与内容要点、风格参考、约定；
  3. **状态**：已存在（给出路径）/ 缺失 / 推断占位（注明转换时的假设，如“暂按现有背景处理”）。
- **`Assets/` 源素材检索与复用**（盘点时先于占位执行；授权内自主行为，`Assets/` 与 `assets/` 是两个目录）：
  - 检索范围与方式：仓库根 `Assets/`（`Game/` 的上一级，原画/素材源目录；`Assets/Image/…` 按 `Assets/Image/分类规则.md` 分层存放，如图片素材在 `Assets/Image/Scene/Background|StillLife|Item|Portrait|UI`）。agent 只按**文件名语义**判断是否匹配该行所需素材，**不得读取或查看图片内容**；
  - 命中合适者 → 允许**复制**到运行目录 `Game/assets/`（数据中以 `assets/…` 引用）并**自行改名**：ASCII、语义化、按素材角色命名（例：`Assets/Image/Scene/Background/7号车厢.png` → `assets/carriage-07.png`）；**不得覆盖 / 替换 `assets/` 既有文件**，撞名时自行加区分后缀；
  - 该行状态记为「已存在（`assets/…`，复制自 `Assets/Image/…`）」，供审阅者确认；若审阅者不采纳（改指其它素材 / 委托占位 / 暂缓），agent 在落地前**删除自己复制且未被引用的文件**（清理自产副本，不影响源目录）；
  - **`Assets/` 严格只读**：仅允许读取与复制源文件；禁止对 `Assets/` 下任何文件做移动、删除、改名、编辑、写入；复制来源与目标记入执行台账（溯源），新增文件列入闸门 2 diff 一并确认；
  - 未命中 → 该行走常规流程（缺失 / 推断占位 → 审阅者四选一）。
- 审阅者结果（四选一；**留空 = 闸门 1 未过**，agent 停下追问）：
  - **沿用**：确认使用既有素材文件；
  - **新建**：给出文件名与内容 / 风格描述（agent 落地时据此登记素材引用，不自行生成文件）；
  - **委托占位补位**：不提供素材，委托 agent 在 `assets/` 下**新增简单占位 SVG** 并自行命名（生成约束见下）；
  - **本行暂缓**：注明影响——依赖该素材的候选事件整体不落地（对应条目记“跳过”）。
- **占位 SVG 生成约束**（仅当审阅者勾选「委托占位补位」时授权）：
  - 定位与格式：落在 `assets/` 下的 `.svg`；内容为简单几何 / 纯色占位示意即可，可加简短文字标签说明用途，不追求成品观感；
  - 命名：ASCII、语义化、建议 `placeholder-` 前缀（如 `placeholder-corpse-hotspot.svg`），遵循 §10 的 id 风格，不得与既有文件重名；
  - 文件内加 XML 注释 `<!-- placeholder: <用途>，正式素材待替换 -->` 标明占位身份；
  - 流程约束：授权仅限所勾选的那一行素材；agent 不得借机生成无关素材，**不得改动任何既有素材文件**；新增文件列入闸门 2 的 diff 一并确认，汇报时列出新增清单；正式素材到位后由用户或后续批次替换引用。
- 本批候选无素材依赖时：正文注明“本批候选无素材依赖”，由审阅者确认后放行。
- 音效 / 舞台演出等框架未支持项（类别 F）不是 JSON 素材依赖，不进本区，按提问处理。
- 素材引用的实际写入与「委托占位补位」新增的 SVG 文件，仍走闸门 2 逐文件 diff 确认（§11 / §17）：本区指定是审阅决策依据，不是免检授权。

### 13.6 约定级条目降频（消除重复审批）

- 约定类登记（如 §7 的「约定 C1」）属“语义确认”，原则上每份剧本确认一次即可。首次出现 → 生成一条人话提问；若 `docs/conversion-reviews/` 历史清单中该约定已被批准且未见变更 → 本批只合并出一条「沿用上次已批准的约定？」确认；用户勾「需要调整」才重开完整约定提问。

### 13.7 读取与消费规则（用户作答 → agent 重读继续）

- agent 生成清单后**停在第 1 闸门**并告知路径与待办概览（N 条提问、M 行素材）；审阅者直接在文件上勾选作答、写「说明」/「补充说明」，然后回复固定口令（“已修改，继续”等，见模板收尾）。
- agent **重读前先校验通过条件**：全部提问有答复（同意 / 需要调整 / 本次跳过）且素材区每行有显式结果（§13.5）；不满足 → 停下逐条追问，不进入执行。
- 满足后按 §13.3 逐条执行；执行完把「用户答复 / 状态」补记进执行台账，可追加“→已落地（日期）”审计标记，但**不覆盖审阅者写下的任何内容**。
- 类别 F（框架缺口）与 G（文本问题）：agent 主动建议勾「本次跳过」并说明去向，不阻塞本次数据落地。
- 落地阶段见 §17 闸门 2/3：仍须先展示逐文件 diff 供确认，终审后才提交。

## 14. 多文件输入

- 多个文件的关系先问清（连载/版本/并列）。
- 编号冲突：若各自编号体系独立 → 需要用户指定命名空间前缀；否则停止询问。
- 并列文件中互相引用的“→E-0xx”目标若在另一文件 → 视同悬空处理并询问。

## 15. 隔离编译验证步骤（每次输出必做）

```powershell
$tmp = Join-Path $env:TEMP ("game-convert-verify-" + [guid]::NewGuid())
Copy-Item -Recurse .\* $tmp            # 在仓库根（Game/）执行
# 1) 把候选 JSON 片段追加到 $tmp\data\events.json（与既有数据合并）
# 2) 若片段引用切片外事件/场景：注入最小隔离占位（空动作事件/示例场景），仅存在于 $tmp
Push-Location $tmp
node .\tools\compile-data.mjs            # 必须输出“编译完成”且退出码 0
Pop-Location
Remove-Item -Recurse -Force $tmp
```

- 若合并后编译报错，一律视为转换缺陷：修复候选后重跑；不允许“关掉校验蒙混”。
- 真实仓库的 `data/` 与 `compiled-game-data.js` 在验证过程中保持不变；落地需人工执行真实 `npm run compile`。

## 16. 阻断情形一览（停下询问，不猜测）

1. 输入未指定/不可读/不是剧本；
2. 事件编号无法辨识；来源编号与既有或他文件冲突；
3. 跳转目标（→/选择/SAN 分支）指向不存在的来源事件（疑似笔误，如“→E-01X”查无此事件）；
4. 分支归属无法判定（文本既不像某分支专属又不像公共，且严重影响接线）；
5. 用户要求的“落地”超出白名单或涉及删除既有内容；
6. 输入含非文本结构（表格语义无法映射时，登记类别 G/O 并询问）。

## 17. 落地模式（landing）与三段确认闸门

- 本 skill **不设配置文件授权开关**：是否允许写 `data/` 由 SKILL.md 的三段闸门逐次批准决定。每次运行默认停留在候选产出（只写审查清单与候选，不写数据文件），任何写入必须先过闸门 2、3。
- 任何转换一律从 candidate 开始，遵守 SKILL.md 的**三段强制确认闸门**，不得跳过或合并：
  1. **第 1 闸门（决策闸）**：candidate 结束——审查清单落盘（人话提问 + 素材指定区 + 执行台账，见 §13）、隔离验证通过后停止；审阅者逐条答复提问、逐行指定素材，**全部完成（§13.5 / §13.7 的通过条件）后才视为过闸**；
  2. **第 2 闸门（改动方案确认闸）**：审阅者逐条答复提问、完成素材指定并明确进入 landing 后，先展示逐文件 diff 草稿供逐文件确认；确认后才允许按 §11 白名单写入 `data/events.json`（`scenes/items/meta` 每处仍须单独人工确认）；
  3. **第 3 闸门（终审闸）**：真实仓库执行编译（报错即回滚修复）后汇报，用户终审通过才可提交 git。
- 与既有旧转换区段（如现行 `events.json` 中 E_CHECK_* 演示与转换事件）的关系处置属于用户决策，落地前必须询问，转换器不自动判断删除或改写。
